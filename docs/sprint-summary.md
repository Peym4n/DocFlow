# DocFlow – Sprint 1 Documentation & Usage

**Project:** DocFlow – Document Management System  
**Course:** SWEN3 | BIF5  
**Sprint:** 1 – Project Setup, REST API and Data Access Layer  
**Backend:** Java 25, Spring Boot 4.1.1, Maven 3.9.x  
**Status:** Core REST API and persistence implemented; see [Open items](#10-open-items-before-sprint-1-submission).

## 1. Project overview

DocFlow is a document management system intended to support document archiving, OCR, full-text search and AI-generated summaries in later sprints. Sprint 1 establishes the Java REST API and persistence layer.

**Sprint 1 scope implemented:** Document *metadata* management. PDF binary upload, OCR, RabbitMQ, MinIO, Elasticsearch and generative AI are **not** part of this implementation yet.

## 2. Implemented functionality

- Java 25 Spring Boot application built with Maven.
- REST API for creating, listing, retrieving, updating and deleting document metadata.
- PostgreSQL persistence using Spring Data JPA and Hibernate (repository pattern).
- Layer separation: controller → service → repository → database.
- `DocumentRequest` and `DocumentResponse` DTOs, mapped using `DocumentMapper`.
- Jakarta Bean Validation for incoming document metadata.
- Unit tests using JUnit 5 and Mockito; REST-controller tests using MockMvc, without using the production database.
- Dockerfile for backend image and Docker Compose for backend + PostgreSQL.

### Document metadata

| Field | Java type | Notes |
| --- | --- | --- |
| `id` | `Long` | Generated by the database; response only |
| `filename` | `String` | Required, nonblank, maximum 255 characters |
| `contentType` | `String` | Required, nonblank, maximum 255 characters |
| `description` | `String` | Optional, maximum 255 characters |
| `createdAt` | `LocalDateTime` | Set automatically by Hibernate when persisted; response only |

The API stores **metadata records**, not the contents of PDF files. The current validation checks whether `contentType` is nonblank and within the length limit; it does not verify MIME syntax or PDF contents.

## 3. Architecture

```text
HTTP client
    │ JSON
    ▼
DocumentController
    │ DocumentRequest / DocumentResponse
    ▼
DocumentMapper   (DTO ↔ Entity mapping at the API boundary)
    │
    ▼
DocumentService  (application logic)
    │
    ▼
DocumentRepository (JpaRepository<Document, Long>)
    │ Spring Data JPA / Hibernate / JDBC
    ▼
PostgreSQL
```

**Responsibilities:**

- **Controller:** HTTP routes, request validation, response status and DTO conversion.
- **DTOs:** Public request and response format; clients cannot directly specify `id` or `createdAt` through the request DTO.
- **Mapper:** Conversion between DTOs and the JPA entity.
- **Service:** Document operations, including not-found handling.
- **Repository:** Database operations provided by Spring Data JPA.
- **Entity:** Maps document metadata to a relational table.

## 4. REST API reference

Base URL for local development: `http://localhost:8080`

| Method | Endpoint | Description | Success | Not found |
| --- | --- | --- | --- | --- |
| `POST` | `/api/documents` | Create document metadata | `201 Created` | — |
| `GET` | `/api/documents` | List all document metadata | `200 OK` | — |
| `GET` | `/api/documents/{id}` | Get one document | `200 OK` | `404` |
| `PUT` | `/api/documents/{id}` | Replace editable metadata | `200 OK` | `404` |
| `DELETE` | `/api/documents/{id}` | Delete document metadata | `204 No Content` | `404` |

Invalid POST/PUT requests (e.g. blank `filename`) return `400 Bad Request` when validation is enabled. PUT currently updates `filename`, `contentType` and `description`; it preserves `id` and `createdAt`.

### Request JSON (`DocumentRequest`)

```json
{
  "filename": "invoice.pdf",
  "contentType": "application/pdf",
  "description": "Electricity bill"
}
```

### Example response (`DocumentResponse`)

```json
{
  "id": 1,
  "filename": "invoice.pdf",
  "contentType": "application/pdf",
  "description": "Electricity bill",
  "createdAt": "2026-10-12T13:00:00"
}
```

`id` and `createdAt` above are examples; actual values come from the database/Hibernate.

## 6. Usage – run the entire application with Docker Compose

Run commands from the **repository root** (the directory containing `docker-compose.yml`):

```bash
# Build the backend image and start backend + PostgreSQL
docker compose up --build -d

# Check container status
docker compose ps

# Follow backend logs, if needed
docker compose logs -f backend
```

REST API: `http://localhost:8080/api/documents`

In the supplied Compose design, the backend connects to the database service named `db` using `jdbc:postgresql://db:5432/docflow`. Docker Compose waits for PostgreSQL's health check before starting the backend.

Stop containers (persisted database volume is kept):

```bash
docker compose down
```

**Warning:** `docker compose down -v` also removes the PostgreSQL volume and its stored data. Do not use it unless you intentionally want to reset local data.

## 7. Usage – run Spring Boot locally, PostgreSQL in Docker

For development/debugging with IntelliJ IDEA:

```bash
# From repository root: start only the database
docker compose up -d db

# From the backend directory: start Java locally
cd backend
mvn spring-boot:run
```

Local `backend/src/main/resources/application.properties` uses the database host `localhost` and port `5432`, whereas the Dockerized backend uses `db` through environment variables in `docker-compose.yml`.

**Do not run the Dockerized backend and local Spring Boot simultaneously on port 8080.** To switch from full Compose to local Java, stop the backend container from the repository root:

```bash
docker compose stop backend
```

Then run `mvn spring-boot:run` from `backend/`.

The provided local development database uses example credentials `docflow` / `docflow` and database `docflow`. **These credentials are for local development only**; do not reuse them in production. Before publishing or deploying, replace hard-coded credentials with environment variables or secret management.

## 8. Usage – sample API calls

Execute these while the backend is running. The ID `1` in the examples must be replaced with an existing ID returned from the POST response, because database IDs are auto-generated.

**Create metadata**

```bash
curl -i -X POST http://localhost:8080/api/documents \
  -H 'Content-Type: application/json' \
  -d '{"filename":"invoice.pdf","contentType":"application/pdf","description":"Electricity bill"}'
```

**List all documents**

```bash
curl -i http://localhost:8080/api/documents
```

**Retrieve one document**

```bash
curl -i http://localhost:8080/api/documents/1
```

**Update metadata**

```bash
curl -i -X PUT http://localhost:8080/api/documents/1 \
  -H 'Content-Type: application/json' \
  -d '{"filename":"invoice_updated.pdf","contentType":"application/pdf","description":"Updated invoice"}'
```

**Delete metadata**

```bash
curl -i -X DELETE http://localhost:8080/api/documents/1
```

**Verify validation (`400 Bad Request` expected)**

```bash
curl -i -X POST http://localhost:8080/api/documents \
  -H 'Content-Type: application/json' \
  -d '{"filename":"","contentType":"application/pdf","description":"Invalid example"}'
```

**Check persisted rows** directly in PostgreSQL:

```bash
docker exec -it docflow-db psql -U docflow -d docflow
```

Inside `psql`:

```sql
SELECT * FROM document ORDER BY id;
```

Exit using `\q`. You can also browse the `docflow` database and `public.document` table with IntelliJ IDEA's Database tool window (where available).

## 9. Tests

The application uses JUnit 5, Mockito and MockMvc.

- `DocumentServiceTest`: tests create, list, retrieve by ID, update and delete; mocks `DocumentRepository` to avoid accessing PostgreSQL.
- `DocumentControllerTest`: tests REST routing, response bodies, HTTP status codes, including not-found cases; mocks `DocumentService` with MockMvc standalone setup.
- Request validation has a controller test ensuring invalid input returns `400` and the service is not called.
- `BackendApplicationTests`: context-loading test; unlike the isolated tests, it currently requires the configured PostgreSQL database to be available.

From the `backend/` directory:

```bash
# Run isolated Service + Controller tests (no database required)
mvn -Dtest=DocumentServiceTest,DocumentControllerTest test

# Run the full test suite (ensure PostgreSQL is running first)
mvn test

# Build/package the application (runs tests unless explicitly skipped)
mvn clean package
```

Test coverage was reported as high during development, but **no exact coverage percentage is documented here**. To report a measurable coverage value, use a coverage tool such as JaCoCo and include its generated report.
